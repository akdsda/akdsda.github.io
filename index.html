멀티도메인 Text-to-SQL AI 챗봇 데이터 아키텍처 구축 및 운영Multi-Domain Text-to-SQL AI Chatbot: Data Architecture & Operations

마케팅 등 유관부서는 여러 도메인의 데이터를 결합해 보려면 매번 데이터 요청을 거쳐 반나절~하루를 기다려야 했습니다. 그렇다고 SQL 작성을 LLM에 통째로 맡기면 비슷한 테이블 중 엉뚱한 것을 고르거나, 조회하지 않은 숫자를 지어내거나, 기간 같은 가정을 숨긴 채 답했습니다. 업무 판단에 쓰이는 숫자라면 틀린 답은 "모른다"보다 위험합니다. Marketing and other teams had to file a data request and wait half a day to a full day whenever they needed numbers that combined several domains. Handing SQL entirely to an LLM wasn't the fix either: it picked the wrong one among look-alike tables, cited numbers it never queried, and silently assumed date ranges. When numbers drive business decisions, a wrong answer is more dangerous than "I don't know."

설계 원칙 — 정할 수 있는 것은 코드가 정하고, 표현이 다양해 규칙으로 못 덮는 판단만 LLM에 맡깁니다. 숫자는 실제 조회 결과에서만 나오고, 가정한 것은 반드시 답에 밝힙니다. Design principle — code decides everything that can be decided deterministically; the LLM handles only the judgment calls rules can't cover. Every number comes from an executed query, and every assumption is disclosed in the answer.

접근Approach
  • 매출·유입·상담·광고·기획전 5개 도메인과 외부 지표를 아우르는 54개 BigQuery 테이블을 하나의 자연어 질의 창구로 연결 (Gemini on Vertex AI · Cloud Run · GCS 메타데이터 캐시)
  • 테이블 설명·실제 컬럼 목록·업무 용어집·과거 질문-SQL 예시를 메타데이터로 관리하고, 질문마다 필요한 테이블 설명만 골라 LLM에 전달
  • 규칙과 LLM이 같은 테이블을 가리킬 때만 확정하는 지표 사전, 정형 질문은 LLM 없이 코드가 만드는 템플릿 SQL
  • SQL 실행 전 가드레일과 오류 기반 자기수정 루프, 답변 숫자의 근거 검증과 가정을 밝히는 안내 배지
  • 동시 요청 대기열 · 사용자별 일일 조회 한도 · 비용 장부 · 감사 로그 · 골든셋 회귀 테스트로 운영 안정성 확보
  • Connected 54 BigQuery tables — 5 domains (sales, traffic, consultations, ads, promotions) plus external indicators — behind a single natural-language interface (Gemini on Vertex AI · Cloud Run · metadata cache on GCS)
  • Managed table descriptions, live column lists, a business glossary, and past question→SQL examples as metadata, sending the LLM only the descriptions of the tables each question needs
  • A metric dictionary that locks in a table only when rules and the LLM agree, plus code-generated template SQL for routine questions (no LLM call)
  • Pre-execution SQL guardrails with an error-driven self-correction loop; answers pass a number-grounding check and carry badges that disclose assumptions
  • Operational hardening: request queueing, per-user daily query quotas, a cost ledger, audit logs, and golden-set regression tests

04적용 4 · 7단계Applied at Steps 4 · 7

If the data doesn't exist or the user lacks access, it says so plainly instead of guessing. When it answers with a substitute metric, it says that too.

05적용 3 · 6단계Applied at Steps 3 · 6
권한과 원본은 코드가 지킨다Permissions and source data are enforced in code

허용 테이블 밖을 읽는 SQL은 실행 전에 막고, 조회(SELECT)만 허용해 원본 데이터는 절대 바꾸지 않습니다.

SQL that touches tables outside the user's allowlist is blocked before execution, and only SELECT is allowed — source data is never modified.

06적용 8단계Applied at Step 8
중요한 안내는 코드가 붙인다Critical disclosures are attached by code

프롬프트로 "기간을 밝혀라"고 지시만 하면 절반 가까이 빠뜨렸습니다. 그래서 기간·범위·기준 배지는 코드가 직접 붙입니다.

Told only to "state the period," the model skipped it almost half the time — so period, scope, and basis badges are attached directly by code.
